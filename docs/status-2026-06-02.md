# c802 prototype status — 2026-06-02

## Purpose

This document records what existed in the desktop c802 prototype on 2026-06-02. It distinguishes implemented behavior from planned or unvalidated research claims.

## Implemented behavior

### Capture and pose tracking

- Rear-camera request at 640×480 through MediaPipe camera utilities.
- MediaPipe Pose with model complexity 1.
- Minimum detection and tracking confidence set to 0.7.
- Live FPS display.
- Average torso visibility check before accepting motion data.
- Per-frame comparison of left- and right-side landmark visibility.

### Signal processing and timing

- 3D vector angle calculation using landmark x, y, and z coordinates.
- Two cascaded second-order low-pass sections, forming the intended fourth-order Butterworth filter.
- Filter cutoff set to 10 Hz and coefficients adjusted from observed FPS.
- Natural cubic-spline reconstruction of knee and elbow angle samples.
- Reconstructed curve evaluated every millisecond.
- Knee maximum extension velocity and estimated elbow-extension onset used to calculate Δt.
- A hard-coded target interval of 50–150 ms.

### Experimental interface

- Auditory intervention mode.
- Visual-feedback comparison mode.
- Baseline mode.
- One-second delay before feedback.
- 800 Hz sine Ding for an in-range result.
- 150 Hz sawtooth Buzz for an out-of-range result.
- Knee and elbow velocity chart in visual mode.
- Trial history with Δt, result, and local time.
- SD and coefficient-of-variation display.
- CSV download.

## Not yet verified

- Accuracy of pose landmarks for the intended camera positions and shooting speeds.
- Accuracy of the knee peak and elbow onset event definitions.
- Accuracy of Δt relative to 240 fps manual annotation or motion capture.
- Validity of the universal 50–150 ms range for the intended participant population.
- Effective source-video frame rate and end-to-end feedback latency across devices.
- Whether the auditory condition improves retention, consistency, cognitive load, or shooting outcomes.

## Known data-integrity issues before formal experiments

1. `shotHistory` combines trials from all three modes, so displayed SD/CV are not condition-specific.
2. CSV output omits participant ID, session ID, condition, trial order, device, FPS, and side.
3. Changing the mode does not begin a separate experimental block or clear statistics.
4. Baseline mode still assigns and displays Δt before applying the mode-specific response.
5. Left/right selection can change during a shot and introduce a discontinuity.
6. Data exists only in browser memory until CSV is downloaded.

## Recommended next engineering checkpoint

Before collecting participants' data:

1. Lock the selected body side for each complete shot.
2. Introduce participant, session, block, condition, and trial identifiers.
3. Keep statistics separate by condition and experimental block.
4. Ensure baseline mode provides no visible or audible knowledge of results.
5. Record actual FPS, dropped frames, landmark visibility, and quality flags with every trial.
6. Build a recorded-video replay harness and a small set of deterministic signal-processing tests.
7. Compare detected events with independently annotated 240 fps recordings.
